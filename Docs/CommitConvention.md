## 커밋 방식
- 형식: [타입] 요약

## 타입

| 타입 | 언제 쓰나 | 예시 |
|---|---|---|
| `[Feat]` | 새로운 기능 추가 | `[Feat] 몬스터 부채꼴 시야 감지 추가` |
| `[Fix]` | 버그 수정, 동작 변화 없는 코드 정리, 동작 변화 없는 구조 개선 | `[Fix] 체력이 0 이하에서 사망 처리되지 않던 문제 수정` |
| `[Docs]` | 문서 작성·수정 | `[Docs] 작업일지 2026-09-20 추가` |

## 요약 줄 규칙
- 가장 중요한 것은 명사형으로 끝낸다. 마침표는 찍지 않는다.
- 50자 이내로 쓴다.
- 무엇을 했는지 이 줄만 보고 알 수 있어야 한다.

```
[Feat] 플레이어 상호작용 기능 추가      (O)
[Feat] 플레이어 상호작용 기능 추가함     (X)
[Feat] 플레이어 상호작용 기능 추가.     (X)
```

## 본문
"무엇을 했는가" 만으로 부족할 때만 쓴다. **왜 그렇게 했는지**, 무엇을 대신 포기했는지는 코드에 남지 않으므로 본문에 적는다.

```
[Refactor] 몬스터 시야 판정을 별도 메서드로 분리

Update 안에 섞여 있던 각도·거리 계산을 한곳에 모음
추적 상태에서도 같은 판정을 쓰게 되어 중복이 사라짐
```

이슈를 쓰고 있다면 본문 마지막에 붙입니다.

```
[Fix] 퍼즐 진행도가 갱신되지 않던 문제 수정

Closes #12
```

브랜치에 커밋한 시점에는 이슈가 닫히지 않습니다. **그 브랜치가 PR로 `main` 에 병합되는 순간 닫힙니다.** 바로 닫히지 않는다고 잘못 적은 것이 아닙니다.

## 커밋 단위
<mark>하나의 커밋에 하나의 작업</mark>이 원칙입니다.

- **리뷰하기 쉬운가.** 여러 작업이 뭉친 커밋은 읽는 사람이 무엇부터 봐야 할지 알 수 없습니다.
- **되돌리기 쉬운가.** 다섯 중 하나만 문제가 되었을 때, 뭉쳐 있으면 나머지 넷까지 되돌아갑니다.

한 파일 안에 성격이 다른 변경이 섞였다면 GitHub Desktop의 **줄 단위 커밋**을 씁니다. diff 화면에서 커밋에 넣을 줄만 골라 두고 커밋하면, 고르지 않은 줄은 남습니다.

## 나쁜 예시

**형식을 갖추지 않은 경우**

```
수정
ㅁㄴㅇㄹ
[Chore] asdf
```

**형식은 갖췄지만 내용이 없는 경우**

```
[Fix] 버그 수정
[Feat] 기능 추가
[Refactor] 코드 정리
```

**한 커밋에 여러 작업이 뭉친 경우**

```
[Feat] 몬스터 패트롤, 시야 감지, UI 수정, 버그 수정
```

마지막은 형식을 갖췄는데도 문제입니다. 고칠 방법은 메시지를 다듬는 것이 아니라 **커밋을 넷으로 나누는 것**입니다.

## 적고 나서 확인할 것
- 이 커밋을 되돌리면 무엇이 되돌아가는지 이 줄만 보고 알 수 있는가
- 같은 파일을 고친 다른 커밋과 이 줄만으로 구분되는가
- 타입과 요약이 서로 맞는가

## 주의사항
- 절대 main과 main-develop에서 직접적인 커밋을 금지한다.
