# Pull Request

작업한 브랜치를 `main-develop` 에 합치는 유일한 통로입니다. `main-develop` 에는 직접 push하지 않습니다.

Phase 단위가 끝났을 때는 

## 운영 방식

| 항목 | 규칙 |
|---|---|
| 리뷰어 | 자신을 지정합니다 |
| 병합 | 승인이 나면 지정된 리부어가 `Merge pull request` 를 진행한다 |
| 병합 후 | 이슈를 닫고 브랜치를 원격·로컬 모두 지웁니다 |

리뷰가 밀리면 다른 사람의 작업이 멈춥니다. 자세히 못 보겠으면 "이 부분만 봤다" 고 적고 승인해도 됩니다. 아무 반응 없이 병합하지 말 것.

---

## PR 만들기
1. 브랜치를 `Push origin` 합니다.
2. GitHub 저장소 화면에 뜨는 `Compare & pull request` 를 누릅니다.
3. base가 `main-develop`, compare가 개설된 브랜치인지 확인합니다. <mark>방향이 반대면 전혀 다른 일이 벌어집니다.</mark>
4. 제목과 본문을 작성합니다.
5. 오른쪽에서 리뷰어를 자신으로 지정합니다.

## 제목

커밋 메시지와 같은 형식을 씁니다.
  → 제목: `[말머리] PR 내용`

- 말머리에 해당하는 키워드는 다음과 같다.

| 타입 | 언제 쓰나 | 예시 |
|---|---|---|
| `[Feat]` | 새로운 기능 추가 | `[Feat] 몬스터 부채꼴 시야 감지 구현` |
| `[Fix]` | 버그 수정, 동작 변화 없는 코드 정리, 동작 변화 없는 구조 개선 | `[Fix] 체력이 0 이하에서 사망 처리되지 않던 문제 해결` |
| `[Docs]` | 문서 작성·수정 | `[Docs] 작업일지 2026-09-20 추가` |

## 본문

담을 내용은 셋입니다.
- **무엇을 했는가**: 변경 항목을 목록으로
- **왜 했는가**: 필요하면 한두 줄
- **확인한 것**: 어떤 상황에서 직접 돌려 봤는지


## 올리기 전 확인

- [ ] Unity에서 실제로 실행해 봤는가
- [ ] 콘솔에 에러가 없는가
- [ ] 관계없는 파일이 같이 들어가 있지 않은가 (특히 다른 사람의 씬)
- [ ] 씬 파일이 들어갔다면, 내가 그 씬의 소유자가 맞는가

## 리뷰하는 쪽

`Files changed` 탭에서 바뀐 부분을 봅니다. 모든 줄을 이해할 필요는 없습니다. 아래 정도만 봐도 충분합니다.

- 이 변경이 **내 작업에 영향을 주는가**
- 내가 만든 스크립트나 프리팹을 건드렸는가
- 씬 파일이 들어가 있는데, 그 씬 소유자가 아닌 사람이 올린 것은 아닌가
- 읽었을 때 **무슨 일을 하는 코드인지 알 수 있는가**

코멘트는 줄 옆의 `+` 를 눌러 그 줄에 답니다. 마지막에 `Review changes` 에서 `Approve`(승인) 또는 `Comment`(의견만) 를 고릅니다.

## 병합
승인이 나면 작성자가 `Merge pull request` 를 누릅니다. 이어서 이슈를 닫은 후 `Delete branch` 로 원격 브랜치를 지우고, GitHub Desktop에서 `main-develop` 으로 이동해 `Pull origin` 합니다.

병합 후 `main-develop` 이 정상 동작하는지 한 번 실행해 봅니다.
